# A project's board, step 4: step limits — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A workflow step may carry `limit = N`: at most N tasks of the project are at that step at
once. A run that reaches a full step waits before it, first in first out, until one leaves.

**Architecture:** Room at a limited step is handed out by the **tasks' drive**, the one drive that
sees every task, the way it already hands out places (`task/queue.rs`). A run about to arrive at a
limited step stops with a new `Action::AwaitRoom` and its drive asks for room (a new effect); the
tasks' drive grants it at once or queues the task, and grants the next waiter when a holder leaves
the step or its run ends. The grant reaches the waiting run as an input through the app carrier.
Rules stay in core; the app only carries.

**Tech Stack:** Rust, GPUI + gpui-component, serde/toml.

**Spec:** `docs/superpowers/specs/2026-11-24-board-design.md` (*Step limits*, *Decided with the
person after the review*)

## Decisions made here

- **Key and value:** `limit = 2` on any step (`StepSpec`, beside `id` and `label`), an integer ≥ 1.
  A file using it is written as `schema_version = 2`.
- **What is counted:** tasks whose setup is the same repository (`setup.repo`) and whose run's
  workflow snapshot has the same workflow id, holding room at that step id. The limit used is the
  asking run's snapshot's. A workflow with an empty id (runs from before ids) is never limited.
- **Holding room:** a run holds room from the moment it is granted until it moves to another step
  or its run ends, whatever ends it. A step it is sent back to, or goes on to, needs room of its
  own if limited. Going back to the same step it holds (a retry of a visit) needs nothing new.
- **Waiting:** the run's previous visit is closed as today; `run.step` becomes the full step, with
  no visit open, `Await::Room` (not persisted). The run is said to wait: note in its session
  `Waiting for room at <label>.`, Tasks page row and board row `Waiting for room at <label>`. The
  budget pauses while it waits and resumes when room comes.
- **Order:** first in first out per step; a task that was already waiting keeps its place.
- **Restart:** room is in memory only. A run that was waiting or holding room comes back cut off,
  as every started run does; its Resume asks for room again before the step starts.
- **Stop / take over** a waiting run: it ends as today and leaves the queue.
- **Board:** a run waiting for room still counts toward the team size (it holds a worktree and a
  team slot). To do pulls only while the board workflow's first step has room:
  `room = min(team - running - starting, first_limit - (holding + waiting at the first step) - starting)`.
- **Board column head:** a limited step's column says `<label> · <n> of <limit>`.

## Global Constraints

- Core GUI-free; rules in core; the app carries effects only (`docs/drives.md`). Exhaustive matches,
  no wildcards. Nothing in core `pub` unless named outside. Comments never cite documents.
- Workflows without `limit` behave and save exactly as before; every existing test passes.
- Validation word for `limit = 0`: `limit is 0: give at least 1, or leave the key out`.
- Files near the split line: `workflow/run.rs` (781), `workflows_page/draft.rs` (737),
  `task/carrier.rs` (651). Put new logic in new files (`task/rooms.rs`, `workflow/run/room.rs`,
  `task/drive/room.rs`), and split a file in the same PR if it passes ~800 lines of code.
- `make fmt`, `make clippy CLIPPY_EXTRA="-- -D warnings"`, `cargo test` before each commit. Known
  parallel flakes that pass alone: `deleting_removes_the_folder_after_the_window_closes`,
  `a_window_closing_writes_the_waiting_burst`, onehand-issues `only_the_newest_write_moves_the_selection`.

## Review Focus

1. **Two runs reach a step with `limit = 1` at once** → one goes in, the other waits and goes in
   when the first moves on. (Test in Task 2, flows.)
2. **The run holding room is stopped, fails or times out** → the next waiter gets room. (Task 2.)
3. **A run waiting for room is stopped** → it leaves the queue; nobody is granted room for it. (Task 2.)
4. **A review sends the work back to `implement` (limit 1) while another task holds `implement`**
   → the sent-back run waits for room at `implement`, and its review's room is released. (Task 2.)
5. **Resume of a run cut off while waiting** → it waits for room again rather than starting the
   step. (Task 2.)

**Interfaces:**
- Consumes: `StepSpec.limit`.
- Produces:
  ```rust
  // core, task/rooms.rs
  #[derive(Debug, Clone, PartialEq, Eq, Hash)]
  pub struct RoomKey { pub repo: PathBuf, pub workflow: String, pub step: String }
  // workflow::Action gains:
  AwaitRoom
  // RunDrive Effect gains:
  AskRoom { key: RoomKey, limit: u32 }     // the run waits until it is given room
  LeaveRoom                                // the run left the step it held room at
  // RunDrive Input gains:
  RoomGiven
  // TasksDrive gains:
  pub fn ask_room(&mut self, task: &str, key: RoomKey, limit: u32) -> Vec<Effect<W>>
  pub fn leave_room(&mut self, task: &str) -> Vec<Effect<W>>
  pub fn waits_for_room(&self, task: &str) -> Option<&str>   // the step id it waits at
  pub fn room_at(&self, key: &RoomKey) -> (usize /*holding*/, usize /*waiting*/)
  // TasksDrive Effect gains:
  GiveRoom { task: String }                // carried as RunDrive Input::RoomGiven to that run
  ```
- Rules: in the Decisions above. `ask_room` grants at once (emits `GiveRoom`) when holders < limit
  and nobody waits ahead, else queues. `leave_room` and `run_ended` free the task's room and drop it
  from any queue, then grant waiters in order while there is room. `Run` on `RoomGiven` opens the
  step's visit and starts it (or, for a resumed run, does what `resume` would have: re-prompt an
  agent step that has its start mark, else start the step).
